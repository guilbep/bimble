# UX map: what the lab shows, what the C core does, and how fast (ticket UXMAP, 26 Nov 2026)

The owner opened the published C lab, tab Setting out, and found survey point, project base point,
true / project north, project zero, levels, grids and reference planes "not implemented", and
Measure "super slow". He asked (1) for a map of every feature the lab shows that is not
implemented yet and (2) for a response under 200 ms for every feature (now ADR 0074).

The record is `ccore/results/ux.md`, generated by `node ccore/tools/ux.mjs` (never edited by hand,
its header says what it supports and what it does not). This file is the study written from it.
A count below is the report's unless the line says otherwise. Run on 26 Nov 2026 on the dev machine
(16 GB aarch64), one headless Chromium with SwiftShader, while another ticket (SETOUT) built in
parallel: the 1-minute load was between 3 and 7 during the runs (each section says it).

## How the map was made

`ux.mjs` builds the lab as GitHub Pages serves it (`vite build` with `VITE_CCORE=1`, the core in
the page as `ccore.wasm`), then, with real input (CDP `Input.dispatch…`) on a freshly loaded page
for every activation, it clicks every control it finds in the page: the title row, the 14 tabs,
every ribbon tab's tools and boxes, the left panel, the view tabs, the viewport's buttons, the
status bar, the panels shown with an element selected, the right-click menu, every key of the key
table, six viewport gestures (select, wheel, orbit, double-click, two view-cube clicks), and every
dialog, page, right panel, menu and tab side panel that a control opens, two levels deep (the File
menu → Settings, About; the palette's 76 commands; the Levels, Materials, History, Quantities,
Project information pages). The second pass does the same against the native host
(`build.sh tcc`, `?ccore=0&native=1`). The verdicts compare the core's answers (`query state`,
`actions`, `measure`, `visibility`, `open_views`, `history`, `settings`) and the page (shell
state, dialogs, page, panels, text, form controls, camera, file chooser, download, new tab) before
and after. A tool is counted as working only when its gesture gives its result (Measure: two
clicks store a measurement; Column, Beam, Wall, Slab: the clicks add an undo step).

## (c) Interactions over 200 ms

**Small model (72 elements), one activation each on the wasm build** (the verdict pass; the
1-minute load was 4.4 at its start, so these are indicative, written with `--force`): of 263
working controls with a time, the median is **45 ms**, the 90th percentile 74 ms, and **4 are over
200 ms**, all camera animations:

| Interaction | ms | Cause |
|---|---:|---|
| Viewport gestures › Drag (orbit, 10 steps of 6 px) | 405 | the whole drag of 10 moves is timed (input of the first move to the frame after the last); per move it is one frame (`perf.md`: orbit frame time) |
| View cube › Home (the button under the cube) | 331 | the camera turns there in 0.3 s by design (`viewcube.ts`: "turns the camera there in 0.3 s") |
| View cube › click the letter N | 324 | the same 0.3 s turn |
| View cube › click its centre | 315 | the same 0.3 s turn |

Next slowest, under 200 ms: a ceiling view opened from the navigator (194 ms), New sheet on the
Sheets page (163), a 3D view or a section made from the New view menu (161, 147), On paper in a
plan (152).

ADR 0074 counts an animation until its last frame, so the view cube's turn breaks the goal by its
own design: either shorten the turn to about 150 ms or count its first moved frame (the turn starts
within one frame). That is the owner's choice; the report keeps the strict number.

**The native host, small model, one activation each** (load 2.7 at the start of its pass): median
**78 ms**, 90th percentile 212 ms; 33 cells over 200 ms, besides the same camera animations: the
Materials page's Add buttons (206–272 ms, 11 of them), New view menu entries (218–315 ms), On paper
(279 ms), Delete (242 ms), P (207 ms), New sheet (221 ms), the language and settings switches
(203–251 ms). The native page talks to the host with synchronous XHR (`bimble.ts` `nativeClient`),
one round trip per call, and these controls make several calls (the action, then `actions`,
`state`, the page's own queries) before they draw: the wasm build does the same calls in-process
for 45 ms median. The native build is the dev loop (`make dev`), not what users get, but the 200 ms
goal applies to it too (ADR 0074): batching the queries that follow an action into one call is the
fix to measure first.

**Large model (20,000 elements):** medians not taken (see the end). The Measure study's click →
frame on it is 259 and 255 ms (below), and `results/large.md` already has an orbit frame of 135 ms
under SwiftShader: every interaction that redraws the model costs at least that much there.

**Measure on large or heavy models: over 200 ms per pointer move** (below): the slowest interaction
found, and the one Pierre hit.

### Measure, per pointer move

Reproduced in the published configuration (the production wasm build, the 3D view, the tool on, 20
pointer moves over the model, then two clicks). "Move → frame" is ADR 0074's response for a
pointermove. Core calls are the wasm module's exports, timed by `ux.mjs` (the page's own calls).

| Model | Elements | Triangles drawn | Move → frame, median (max) | `tool measure_pointer` per move | Click → frame | Load |
|---|---:|---:|---:|---:|---:|---|
| small (`golden/frame.json`) | 72 | 864 | 16 (26) | 2.2 ms | 61, 58 | 3.7 |
| large (`bench/large_model.py 20000`) | 20,026 | 266,520 | 156 (167) | 140 ms | **259**, **255** | 3.1 |
| heavy (`bench/mesh_heavy_model.py 700 1000`) | 772 | 695,264 | 48 (60) | 36 ms | 97, 35 | 3.3 |
| a local imported model (not committed) | 1,749 | 2,212,174 | **556 (991)** | **266 ms** | **760**, **622** | 3.3 |

The owner's case is a local imported model (not committed, not named): 1,749 elements, 2,212,174
triangles drawn: **move → frame 556 ms median, 991 ms max; click → frame 760 and 622 ms; the core's
`measure_pointer` 266 ms of it per move**, one full frame drawn per move (the rest). The synthetic
mesh-heavy stand-in (`ccore/bench/mesh_heavy_model.py 700 1000`: the frame plus 700 proxies of 992
triangles) is fast (48 ms): per-element costs dominate, not triangles: the 20,000 simple prisms of
the large model cost 140 ms per move in the core, the 772 elements of the heavy one 36 ms.

**What runs per pointer move while Measure is on** (read in the code, confirmed by the numbers and
the profile: the five hottest functions are wasm functions inside `measure_pointer`; the wasm is
stripped of names by `wasm-opt`, so the profile shows `wasm-function[448]` etc.):

1. **The core, `tool measure_pointer`** (`ccore/session/measure.c` `cc_measure_snap` →
   `pick_layer`): for **every element** of every layer, `cc_scene_world_mesh` copies and transforms
   the element's whole mesh (positions, indices, edges) into an arena, then the ray is tested
   against **every triangle** (Möller–Trumbore in f64). No bounding-box test comes first. Then the
   mesh of each element hit is built again for the vertex and the edge snap. The cost grows with
   the number of elements and of triangles of the whole model, on every move. (The page's own pick,
   `glviewport.ts` `pickHit`, tests each element's box first and is cheap.)
2. **The page, the status bar's coordinates**: one `query coordinates` per frame at most (0.1–0.6
   ms) after a JavaScript pick: negligible.
3. **A full WebGL redraw** per answer (`dirty = true` in `measureAt`): the whole model is drawn
   again to move a marker that lives on the 2D overlay canvas. Under SwiftShader this is the rest of
   the time: about 15 ms at 72 elements, 16 ms at 20,000 (move 156 ms − core 140 ms), about 290 ms
   on the 2.2-million-triangle model. A GPU draws faster; the redraw is still not needed.

**Proposed fix, not made here** (it is in `ccore/session/`, which ticket SETOUT edits now, and it is
over this ticket's 30-line limit): (1) in `pick_layer`, test the ray against each element's world
box before building its world mesh (the box computed once per scene revision and kept with the
scene's cached view, as the page's `pickHit` does), and build the mesh only for elements whose box

## (d) Why `parity.md` counted 6 "fake UI"

`ccore/tools/parity.mjs` (`fakeUi`, line 838) counts a control as fake only when it is bound to an
action that **Rust enables and the C core never enables** in any of its 13 scenarios, or to a query
that is a stub or missing in C. It never activates a control. So it misses, by construction:

- every ribbon tool with `action: null` and no page, panel or dialog: it lists them apart as "drawn
  disabled on purpose" (55 tools). They are drawn "not yet", which is honest, but they are the
  missing features: Survey point is one of them;
- the 2 ribbon boxes (they are not tools in its parser);
- a control bound to a page or a panel (it drops `opens page|panel` places): whether the page then
  works is not looked at (Phases, Sub-projects, Users and Graphic standards open "not available");
- a control whose action the C core enables but whose effect is nothing or a silent refusal;
- a tool that starts but whose gesture gives nothing;
- everything outside the ribbon's static data and the actions: the left panel, the pages' own
  buttons, the dialogs, the menus' non-action entries.

**Proposal.** Keep `parity.mjs` for what it proves (names, flags and shapes against Rust) and rename
its line to "Rust-enabled actions the C core never enables (6)" so no one reads it as the lab's
fake-UI count. The count of the user's experience is `ux.mjs`'s: `dead + error` (broken) and `says
not available` (honest, missing). `parity.md` can quote `ux.md`'s counts with its commit.
`parity.mjs` is not changed in this ticket (a rename of one line is the owner's call).

## How `ux.mjs` should gate, later

Not in `ccore/ci/run.sh` now (it would fail today). In this order:

1. `ux.mjs --check` (wasm, small model, verdicts only, about 10 minutes) in `ci/run.sh full`: fails
   when `dead` or `error` grows beyond the committed report; the committed number goes down ticket by
   ticket to 0.
2. Then `dead == 0` and `error == 0` (errors that are validation messages excluded by name).
3. Then the 200 ms budget on the small model for every working control, once the slow list is short
   and the runner's load is read first (a run above load 4 writes no numbers).
4. The large model last, with ADR 0074 rule 4 (progress within 200 ms) where it cannot meet it.

## What this study did not do, and the tool's limits

- **Timings, medians of 5:** not taken. The machine's 1-minute load stayed between 3 and 7 all
  session (ticket SETOUT building beside this one); one median run on the wasm build was started
  and stopped to leave time for the verdicts of both builds. The report's response times are the
  one activation of the verdict pass ("ms 1 run"), written with `--force` and marked indicative.
  To do with the machine idle: `node ccore/tools/ux.mjs --timing-only --merge ccore/out/ux/ux.json`
  (the small model, then the large one: the ribbon, the keys, the viewport and the title row only,
  since a page load takes seconds at 20,000 elements).
- **The native host's Measure study** was not run (the wasm build is what Pierre used).
- **Controls three levels deep**, text fields and selects (58 "not exercised": typing a value is
  not driven), the small-screen layout, French.
- **Tool limits that may show as "dead"**: a plan's camera is not in `__bbGl` (Fit all in a plan
  view looks dead after a zoom); a control already current (the View tab, the 3D view tab) is
  "not exercised"; a click on an element's list row in a page that only moves the focus.
- **The `wasm-function[N]` names** in the profiles: `wasm-opt` strips the names; a build with a
  name section would name them (they are all inside `measure_pointer`, by the call timing).
- **The status bar's EN / FR switch** changes the tabs' names, so the tool explored the left panel
  again under "the tab FR" and "the tab EN": 2 extra surfaces, harmless, counted.
- **Run times:** the wasm verdict pass and the Measure study on three models, 656 s; the native
  verdict pass, about 760 s; the local model's Measure, about 3 minutes. A fresh page per activation
  (median 820 ms per load) is most of it.
- **No fix was made** (the page was not changed; the Measure fix is described in (c)).
