# Research: why the browser build grew from 14 to 22 MB

_20 Nov 2026. STUDY station (Opus), both refs built side by side on rustc 1.100.0 and wasm-bindgen
0.2.130, release profile, no wasm-opt. Sizes from `twiggy top`, grouped by crate._

## Measured

| Ref | Before wasm-bindgen | After | gzip -9 |
|---|---|---|---|
| v0.5.0 | 15 839 215 B | 14 068 558 B | 4 340 455 B |
| HEAD 501b597 | 23 942 970 B | 22 211 103 B | 6 856 750 B |

No `[profile.*]` section changed: opt-level 3, no LTO, 16 codegen units, panic already `abort` on
wasm32. The growth is content, not the toolchain.

- 49 crates entered the browser build since v0.5.0. Most come from `lopdf` (aes, cbc, md-5, sha2,
  chacha20, brotli-decompressor, nom, unicode-normalization) and `dxf` (chrono, encoding_rs).
- `wasm-bindgen --remove-name-section` on HEAD: 18.05 MB raw, 6.29 MB gzip (saves 4.16 MB raw, 0.57
  MB gzip, measured).

## Options (each marked measured or estimate)

1. Strip the name section in release builds: measured, -0.57 MB gzip. Cost: stack traces in the
   browser lose function names. `wasm-opt` without `-g` likely does the same (inference). Binaryen
   is not installed on CI.
2. DXF and PDF reference plans (ADR 0021) behind a cargo feature that the web build leaves out:
   estimate -1.0 to -1.5 MB raw. Cost: no reference plans in the browser.
3. A wasm release profile with `opt-level = "s"`, `lto = true`, `codegen-units = 1`: estimate 15 to
   30 % smaller. Cost: longer builds. Not measured.
4. ciborium (binary `.bimble`): its deserializer is 0.23 MB, measured. Needed to open binary
   `.bimble` files in the browser.

Commands: `cargo build -p bimble-web --target wasm32-unknown-unknown --release`, `wasm-bindgen
--target web --no-typescript [--remove-name-section]`, `twiggy top -f csv`, `cargo tree --target
wasm32-unknown-unknown -p bimble-web -e normal` diffed between refs.

## Measured after T7a

Same machine, `scripts/build-web.sh` (release), no `wasm-opt` installed. Gzip is `gzip -9`.
Build time is wall clock for the whole script; the baseline and step 2 reuse the cached
release build, the profile builds compile everything from scratch for the new profile.

| Step | Raw bytes | Gzip bytes | Build time |
|---|---|---|---|
| Baseline (`--release`) | 22,211,103 | 6,856,705 | 41.7 s |
| + `--remove-name-section` | 18,051,931 | 6,286,167 | 0.9 s (cached cargo build) |
| + `[profile.web]`, `opt-level = "s"`, LTO, 1 codegen unit | 16,058,934 | 5,364,684 | 37.3 s |
| + `[profile.web]`, `opt-level = "z"`, LTO, 1 codegen unit | 14,891,139 | 4,875,869 | 29.1 s |

Kept: name section removed in release, and `[profile.web]` with `opt-level = "z"`: -33 % raw and
-29 % gzip against the baseline, -22 % gzip against step 2. `PROFILE=dev` keeps the names and the
dev profile. The desktop build does not use `[profile.web]`.

Behaviour: the `z` build opened the 72-element demo in headless Chrome (WebGPU), no console error,
"opened frame.bimble: 72 elements, 864 triangles, 0.47 s".

### Size against open time

`z` was 40 % slower to open a large model in a first measurement, so the three profiles were
compared on both. Name section removed in all three; `lto = true`, `codegen-units = 1` in all
three. Model: `bimble demo X --bays-x 20 --bays-y 20 --storeys 10` (13 261 elements, 159 132
triangles, 583 916 bytes). Open time: the viewer's own log line "opened perf-large.bimble: ... N s",
`viewport.html?url=perf-large.bimble`, headless Chrome (Playwright 1.64.1), a fresh browser context
per run, the variants alternated, 3 runs each. Score = gzip bytes x 8 / 10 Mbit/s + median open (s).

| Profile | Raw bytes | Gzip bytes | Opens (s) | Median (s) | Download at 10 Mbit/s (s) | Score (s) |
|---|---|---|---|---|---|---|
| (a) `opt-level = 3` | 16,494,085 | 6,060,244 | 0.23, 0.22, 0.22 | 0.22 | 4.85 | 5.07 |
| (b) `opt-level = "s"` | 16,058,934 | 5,364,684 | 0.33, 0.33, 0.33 | 0.33 | 4.29 | 4.62 |
| (c) `opt-level = "z"` | 14,891,139 | 4,875,869 | 0.41, 0.41, 0.42 | 0.41 | 3.90 | 4.31 |

Kept: (c) `opt-level = "z"`, the lowest score. Cost: opening is about 1.9 times slower than with
`opt-level = 3` (0.41 s against 0.22 s on this machine; an earlier run on the same model measured
1.48 s against 1.06 s). The download saving is paid once per visit, the open cost once per file;
on a fast link or with the wasm cached, (a) opens faster. Revisit with a cached-load benchmark.

**Decided (Pierre, 20 Nov): opt-level 3 with LTO.** The wasm is cached after the first visit, and
opening a model is paid every time. 6 060 244 bytes gzipped (today 6 856 705), measured again by the
orchestrator.
