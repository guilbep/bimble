# ADR 0074 — Every interaction answers within 200 ms

- Status: Accepted, 26 Nov 2026. Decision by Pierre (owner): "be sure that for each feature we want
  to target < 200ms response time? it's our ux goal". The definition of "response", the models and
  builds, and the rule for an interaction that cannot meet the goal (progress within 200 ms,
  cancellable) were written in ticket UXMAP and accepted under the owner's delegation of the same
  day ("don't wait for me to validate the ADR, just do your best, I'll review once it's
  implemented").
- Concerns: the Vue lab (`web-ui/`), the C core's calls it makes (`ccore/session/calls.c`), the
  record `ccore/results/ux.md` (`ccore/tools/ux.mjs`), the study `docs/research/ux-map.md`.
- Reversal cost: low (a goal and a report; no format changes).

## Context

The owner opened the published C lab and found tools that do nothing (Setting out: survey point,
project base point, true / project north, project zero, levels, grids, reference planes) and a
Measure tool that is "super slow". The parity report counted 6 "fake UI" controls and timed
nothing the user does. There was no number for what a click costs.

## Decision

1. **The goal.** Every interaction of the lab answers within **200 ms**: a click on a control, a
   key of the key table, a tool's click, a pointer move while a tool is on, a page or dialog shown.
2. **What "response" means.** From the input event (the page's `pointerdown`, `keydown` or `wheel`
   event, its `timeStamp`) to the end of the animation-frame callbacks of the first frame that
   holds the last effect of that input (the last DOM change, WebGL draw or core call, after which
   nothing changes for 300 ms); the frame is then handed to the compositor. This is what
   `ccore/tools/ux.mjs` measures. A camera animation counts until its last frame.
3. **Where.** The wasm build that GitHub Pages serves (the production build of the C lab, the core
   in the page) and the native host (`build.sh tcc`), each on the 72-element fixture
   (`ccore/golden/frame.json`) and on the 20,000-element synthetic model
   (`ccore/bench/large_model.py 20000`, `ccore/results/large.md`), headless Chromium at 1280×800.
   Headless Chromium draws with SwiftShader (on the CPU): a number over 200 ms that is all
   SwiftShader draw time is reported as such, not hidden; the goal still applies.
4. **An interaction that cannot answer within 200 ms** (an open of a large file, an export, a
   boolean of a large model) must, within 200 ms of its input, show that it started (a progress
   line, a busy cursor on the control, the step it is in) and must stay cancellable (Esc or a
   Cancel button stops it and leaves the model as before). A pointer move that cannot be answered
   in time drops the older moves (one answer per frame, the latest position), never queues them.
5. **The record.** `ccore/results/ux.md`, generated by `node ccore/tools/ux.mjs`, never edited by
   hand: each control's verdict (works, says not available, dead, error, disabled, not exercised)
   and the response time of each control that works, median of 5, per build and model, each cell
   over 200 ms marked. Numbers are not written when the machine's 1-minute load is above 4.
6. **The gate, later** (not in `ccore/ci/run.sh` yet: it would fail today). First `dead == 0` and
   `error == 0` on the wasm build and the small model (`ux.mjs --check`); then the 200 ms budget on
   the small model, once the list of slow interactions is short; the large model last.

## Nothing fake (CLAUDE.md), today

CLAUDE.md already says: "Nothing fake: what is not served shows 'not available yet'". The controls
that break it at the time of this ADR are listed in `ccore/results/ux.md`, section "Dead" (drawn
enabled, activation changes nothing observable), and in `docs/research/ux-map.md` section (b).
A control drawn "not yet" (dashed, the tooltip) does not break the rule: it is honest, but it is
still a feature missing, and the study counts it.

## Consequences

- Each ticket that adds or changes an interaction runs `ux.mjs` on it and says its number.
- The Measure tool's pointer moves (see the study) are the first interaction to fix.
- The parity tool's "fake UI" count stays a static check; `ux.mjs` is the one that drives controls.
