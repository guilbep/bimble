# 2026-11-08 — IFC import for editing (I3, CLI)

Pierre started I3: "let's start I3! start with the command line, then the interface?" The FAQ in
bimble-docs said converting an IFC into an editable `.bimble` model "is planned"; Pierre read that as
understating a core feature. Decision: it stays "not yet" for the viewer but the CLI conversion ships
now, and the FAQ reword went to bimble-docs PR #6.

## What happened
- **ADR 0032** (import engine): extend the own pure-Rust reader rather than web-ifc or
  IfcOpenShell-with-bindings — one code path for display and import, wasm stays possible, and the
  reader already parses every needed entity. IfcOpenShell stays the test oracle only.
- **Two new generators** (format v2): `ExtrudedPolygon` (outline, voids, height) for non-rectangular
  extrusions, `Mesh` (positions, indices) for explicit geometry (`IfcPolygonalFaceSet`, faceted
  breps). `Generator::profile()`/`depth()` became `extrusion() -> Option<Extrusion>`, so a Mesh
  element can't pretend to extrude. `extrude()` gained hole support (earcut: nv − 2 + 2h triangles),
  and export writes voids as `IfcArbitraryProfileDefWithVoids` and meshes as `IfcFacetedBrep`
  (shared points in first-use order, so output stays deterministic).
- **Import** (`bimble-ifc/src/import.rs`, `bimble import-ifc model.ifc model.bimble`): storeys with
  placements, materials deduplicated by name with `GlobalId::derived` ids and category guessed from
  the grade, units → mm, GlobalIds kept (invalid ones are derived and reported). Rectangle detection
  maps Revit's polyline profiles back to `rect_column` / `rect_beam` / `wall` / `pad_footing` / slab;
  walls get their origin at a short end with x along the long side. Downward extrusions flip the
  frame 180° about local X so `.bimble` always extrudes along +Z. Openings are counted and reported,
  not cut. Everything else lands in the report, never dropped silently.
- **Round-trip test** (`bimble-ifc/tests/roundtrip.rs`): demo frame → export → import gives back all
  72 elements (ids, classes, names, storeys, generator parameters, placements); an L-shaped column and
  an explicit mesh round trip as `ExtrudedPolygon` and `Mesh`; the imported model saves and loads.

## Numbers
- Demo frame: `export-ifc` → `import-ifc` → `info` — 73 elements, 73 parametric, 0 meshes, 4.9 ms load.
- Double round trip (`frame.bimble → IFC → import → .bimble → IFC`) checked with IfcOpenShell
  0.9.0.post1: OK, 73 elements.
- Tests: 196 pass workspace-wide (3 new round-trip), clippy clean.

## First bug worth remembering
The first extrusion check expressed the IFC direction in the wrong frame (world instead of the
solid's own), so every horizontal beam fell back to a Mesh. The extrusion direction is defined in the
solid's frame and the placement frame is that same frame — the check is just `dir ≈ ±z` in solid
coordinates.

# 2026-11-08 (later) — I3 continued: openings, psets, viewer entry

Pierre: "stay on this branch, and continue iterating" — the four remaining I3 items in one pass:
openings cut on import, the viewer entry, the Revit fixture, psets beyond material. CI/test/format

## What happened
- **Openings cut on import**: `Element` gained `openings: Vec<Opening>` (`placement` + `generator`,
  element-local coordinates, both serde-optional so old files keep their hashes). `bimble-geom`
  refactored to f64 triangles: `extrude_tris` (closed solids with outward winding), `mesh_from_tris`
  (welds by bits, flat normals), and `element_tris` = host triangles minus opening cutters through
  manifold3d; a boolean that fails draws the element uncut, like the viewer already did. Import
  tessellates each `IfcOpeningElement` body in world mm (`Reader::product_body`), maps it into
  element-local coordinates (through the storey frame and the host's placement, both orthogonal so
  `Affine::local` is the exact inverse; mesh hosts are storey-relative so only the elevation is
  subtracted), and stores it as a `Mesh` generator with identity placement.
- **Psets beyond material**: `Element.properties: BTreeMap<String, String>` keyed
  `"Pset_Name/Property"` with the value as text (labels, texts, booleans, integers, reals). Import
  walks `IfcRelDefinesByProperties → IfcPropertySet → IfcPropertySingleValue`, skips Bimble's own
  psets, and counts unsupported value kinds in the report. Export groups the keys back into psets
  and writes every value as `IFCLABEL`, so the round trip is text-stable.
- **Viewer entry**: ribbon action "Import IFC…" (Model tab, palette, icon = folder with an arrow).
  On the desktop the file is imported on a thread; in a browser its bytes parse on a later frame.
  The editable copy targets `<stem>.bimble` next to the IFC, so Ctrl S writes the copy, and the
  title bar shows what isn't saved (ADR 0028).
- **Revit-style fixture** (`bimble-ifc/tests/revit_style.rs`): a hand-written IFC4 the way Revit
  writes walls — polyline profiles (no typed rectangle), an `IfcOpeningElement` window void,
  `Pset_WallCommon` (label, boolean, real) and a `Bimble_Generator` pset that must be skipped. The
  import must detect the rectangle, land the opening in element space (checked by bounding box and
  by the volume the boolean removes), keep the properties, and survive a double hop
  (import → export → import → save → load). Plus a round-trip test for a wall with a window and
  psets, and one for an opening on a mesh host.

## Bugs worth remembering
- The pset name was double-quoted on export (`''Pset_WallCommon''`): `string()` already adds the
  STEP quotes. The second import then saw an unnamed pset and dropped the properties — the
  round-trip test caught it.
- Mesh-generator coordinates are element-local (storey-relative), not world: a fixture that stores
  world positions round-trips shifted by the storey elevation. Openings on a mesh host must use the
  same convention (subtract the elevation, nothing else).

## Evening: large models and zoom to cursor
Pierre: a 200 MB electrical IFC crashed the viewer — `Buffer size 742362600 is greater than the
maximum buffer size (268435456)` — and zoom should go where the cursor is, not to the centre.

- **Cause**: the whole scene went into one vertex buffer; wgpu's default limit (WebGL2 and many old
  GPUs too) is 256 MiB per buffer. Not RAM. `bimble render` panicked the same way headless.
- **Fix**: `GpuScene` holds a list of buffers, each within `max_buffer_size`, cut at whole triangles
  and segments (multiples of 6 vertices). Test `scenes_larger_than_a_gpu_buffer_are_split`: a 16 KiB
  limit device draws the demo pixel-identical to the default one; with one buffer it panics.
- **Numbers** (M-series, 24 GB, release, private IFCs kept out of the repo):

  | file | elements | triangles | load | peak RSS (`info`) |
  |---|---|---|---|---|
  | 200 MB electrical | 29 935 | 8.84 M | 3.2 s | 2.5 GB |
  | 335 MB architecture | 30 295 | 5.43 M | 2.2 s | 3.2 GB |
  | 872 MB plumbing | 35 243 | 9.10 M | 6.6 s | 6.8 GB |

  The 200 MB one now renders (`bench`: upload 494 ms, median 7.6 ms / 132 fps at 1080p MSAA 4,
  process 4.0 GB); the 872 MB one renders headless too. One CPU pick (hover, wheel pivot) takes
  ~50 ms on 8.8 M triangles: the next wall, not fixed.
- **Zoom to cursor**: `Camera::zoom_at` scales the camera about a pivot, which stays under the cursor
  (test: perspective, ortho, mirrored, both clamps). The wheel pivot is the picked geometry in 3D,
  the target plane in 2D or over empty space; cached while only the wheel moves the camera, so a
  scroll picks once. The + / − buttons still zoom about the centre.
- Pierre then chose: measure where memory goes first, then a warning only when too big for the
  machine (> 50 % of RAM; the browser counts 4 GB), offering to open one storey / class /
  material; try the resolution knob; GPU picking.

## Memory trace
Method: a counting `#[global_allocator]` (live and peak heap bytes) with a mark after each load
phase, mimalloc swapped out for the run; not committed. Heap, 200 MB electrical file:

| phase | live | peak in phase |
|---|---|---|
| file text | 200 MB | 200 MB |
| STEP parse | 1126 MB | 1293 MB |
| meshing (f64 triangles) | 2057 MB | 2057 MB |
| scene built | 2099 MB | 2113 MB |

Parsed entities cost ~4.5× their text. 121 of 190 MB of that file's text is property sets
(IfcPropertySingleValue, IfcPropertySet, IfcRelDefinesByProperties), which the display never reads.
The two other files are mostly explicit faceted breps (points, polyloops, faces: 3 M faces in the
872 MB one). The trace missed the GPU upload: `bimble render` peaked at 5.6 GB against 2.6 GB for
`info` on the 200 MB file.

Fixes, all keeping the same triangles and edges (peak memory footprint, 200 / 335 / 872 MB files):

| | `info` | `render` |
|---|---|---|
| before | 2.57 / 3.25 / 6.76 GB | 5.57 / 5.10 / 8.98 GB |
| skip property sets, free the text after parsing | 1.67 / 2.63 / 5.37 GB | |
| stream 64 MiB vertex chunks, submit after each | | 3.66 / 4.01 / 7.41 GB |

The submit matters: each `create_buffer_init` staging copy lived until the first frame. `bench`,
200 MB file: process after load 3970 → 1937 MB, frame median unchanged (7.6 ms). The browser path
now takes the bytes and drops them once parsed (wasm has 4 GB at most).

**Resolution knob: does not help these files.** Arc tolerance 0.5 → 2 → 5 mm changes triangles by
< 1 % on all three. The electrical file's 8.8 M triangles are mostly instances: 31 041
IfcMappedItem over 761 IfcRepresentationMap. Meshing each map once and drawing instances would cut
both RAM and GPU memory there; the brep-heavy files need a smaller parsed form (dense or lazy
entity store) instead. Also: the 872 MB file has 9.1 M triangles, near the 10 M read budget.
