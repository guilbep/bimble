## Later: ADR 0038 decided, first slice of Synchronize
- **Q4 conflicts**: ten ways scored (borrowing fit, effort, safety, offline, Revit habits); chosen: a list
  grouped by element, keep mine / keep theirs per element, a row frames its element in 3D; the 3D ghost later.
- **Q5 rights**: viewer / modeller (optionally per layer) / owner, in a versioned `people` object; checked at
  push; advisory on a shared folder, enforced only by a future server. The office's "view"/"model" stays a
  personal mode, local, separate from rights.
- **Borrowing, as read here**: written to the remote when an element is first changed, released when its owner
  synchronizes (Revit's way) — for the office to confirm.
- **Code** (`bimble-core/src/remote.rs`, `bimble history remote|clone|push|sync|borrow`): a remote is a history
  folder on a share; fetch and push copy objects checked against their hash, parents before children; push
  moves the remote branch only forward, under a lock file at the remote's root; sync = fetch, merge, push,
  release borrows, and stops on conflicts or on changes to elements borrowed by someone else. Only push creates a remote; sync and borrow refuse a missing one.
  `write_atomic` now uses a unique temp name (two people writing one object on a share could otherwise rename
  each other's half-written file into place).
- Tests: five two-person scenarios on a temp share (sync both ways, non-fast-forward refused even after fetch,
  stale lock, conflict pushes nothing, borrowed element stops a sync until its owner syncs, damaged remote
  object refused and not copied). Checked that the fast-forward and write-order tests fail on broken code.
- Decided by: Pierre ("I trust you on that") for Q4 and Q5; the choices by Claude.
- Not built yet: per-element resolution (sync has only `--prefer ours|theirs` for all), the `people` object and rights, layers, the

## Evening: the ten optimizations of ADR 0036, measured
Pierre asked for all ten, decisions to review afterwards; a weak GPU is simulated (Mesa's llvmpipe, a CPU
Vulkan driver, in a Linux container capped to 2 cores) instead of waiting for the 2012 MacBook.
- #4 no MSAA while moving: weak GPU 1.8–2.7× faster moving frames; the viewer drops MSAA once a movement
  misses the frame-rate target. None on the M4 Pro (not fill-bound).
- How much is hidden (occlusion queries per element): 36–92 % of the drawn triangles on the whole model.
- #5 occlusion on the CPU: weak GPU −26 to −39 % on the architecture model, nothing on MEP; on the M4 Pro
  it costs 1.5× (CPU raster), so only after a missed target. Two conservativeness bugs caught by the
  pixel test on the way (sub-pixel gaps between occluders, holes along each wall's diagonal).
- #9 proxies per octree cell (geometry by an agent, renderer here): whole-model frames 29.1 → 1.3 ms
  (415 MB) at a 3 px error; used while moving on slow machines.
- #6 edges on screen: lines cost half a frame (30.8 → 8.9 ms without); screen edges 29.1 → 8.6 ms at
  MSAA 1, weak GPU −18 to −23 %; in the viewer's lean moving frames.
- #7 joined draws: 2–13 % fewer draws, no time gained. #8 codec (agent): meshes 3.5–4.4× smaller, decode
  1.5–2.2 GB/s, not used yet. #3: hover overlay kept, size-band redraw dropped (slower).
- Rule that emerged: on a fast GPU the CPU-side tricks cost more than they save; everything for weak GPUs
  switches on when a movement misses the frame-rate target (MSAA off, occlusion, proxies, screen edges).
- #1 GPU occlusion queries (last frame's answers, boxes probed): M4 Pro 335 MB 4.09 → 3.67 ms, free; weak
  GPU −24 % (#5 does better there). Viewer: #1 on native backends keeping the target, #5 on slow machines.
- #10 culling copies on the GPU (compute, indirect draws): neutral on the M4 Pro; an option, not used yet.
- Not tried by hand in the running viewer: the slow-machine path (MSAA off, CPU occlusion, proxies built on
  the first missed target, screen edges), the hover overlay, the GPU-query redraw loop. Tests cover the
  renderer; the switches in the viewer have none.
