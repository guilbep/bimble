# 28 Nov 2026 — ticket MACAPP: the native app on macOS, an unsigned .dmg per architecture

Branch `cc/macapp` from `next` 550d8ff (preview.8 candidate). Pierre decided on 28 Nov 2026: macOS `.dmg` first, then
Windows; unsigned to start; his Apple Silicon MacBook is the human test; Intel on CI only. Claude made the choices
(ADR 0088) on an aarch64 Linux machine, with GitHub's macOS runners as the Mac. The orchestrator pushed each round to
draft PR #103 (`cc/macapp` → `next`) and gave the run ids. `ccore/ci/run.sh native` (8 suites) stayed green on Linux
before every hand-off.

## What happened, in order

- **Shaders first, on Linux.** I built SDL_shadercross and SPIRV-Cross at pinned commits in 37 s
  (`native/macos/shadercross.sh`; no package, no sudo) and translated the 20 committed SPIR-V headers. All 20 translated
  unchanged:
  - the clip-distance variants as `[[clip_distance]]` arrays;
  - hizn / hizn2 as `texture2d<float, access::read_write>` with fences, threadgroup memory and a barrier;
  - seen and ttest reading their textures through samplers (`.read()`).
  shadercross put the bindings in SDL's MSL order. The result is committed as `shaders/gen/*.msl.h`, signed like the
  SPIR-V, and checked by `shaders --check`.
- **ImGui's metallib needs macOS 14.** Its SDL_GPU backend prefers the metallib whenever the device lists it. A
  force-included header makes it take its MSL path, so the deployment target stays 11.0.
- **The CI loop.** `macapp.yml` builds and tests only the mac app, in 4–8 minutes a round. Rows: arm64; x86_64 cross-built
  and run under Rosetta on the same arm64 runner; and an Intel probe. A last job measures the universal image.
- **Round 1** (run 46150628076):
  - Metal is there: "Apple Paravirtual device", Mac2, read-write tier 2, on arm64 and under Rosetta. The Intel runner
    also has a paravirtual device, but no Mac2.
  - `xcrun metal` compiled all 20 MSL files.
  - Static SDL 3.4.18, brotli 1.2.1 and FreeType 2.14.3 built. `shaders --check` and `deps.sh --check` passed under
    macOS's bash 3.2.
  - The build broke on `embed.c`: BSD `od` pads its last line, and sed turned that into `,,`. Fixed with awk.
- **Round 2** (run 46151176806):
  - The app built on all three rows, and the images passed `macapp_test.mjs` 21/0: layout, plist, `codesign --verify
    --strict`, `otool -L` system-only, architectures, minos 11.0, `--version`.
  - `--selftest-window` under Cocoa: device, claim, vsync, OK.
  - Every offscreen run failed with "No supported SDL_GPU backend found!": SDL's offscreen driver has no Metal view. The
    suites said `skipped:`.
  - On Intel, SDL refuses the GPU itself (no Mac2).
  - Sizes measured: ULMO 2.40 MB, ULFO 3.09 MB, UDZO 3.25 MB (arm64); universal 6.39 MB. Decision: two images, ULMO.
- **Round 3** (run 46151797259): offscreen on macOS is now Cocoa with a hidden, unclaimed window. On arm64 and under
  Rosetta:
  - `native_app_test` 81/0 and `native_geo_test` 7/0;
  - the truth test 0 missing everywhere (2,847 orbit-zoom frames on arm64);
  - the fixture 0.12 % from the Linux reference, the far building 0.184 % (limit 0.2 %);
  - Metal validation clean.
- **Round 4** (run 46152304692): the suites became required on arm64 and Rosetta. CI also checked:
  - the crash handler: a SIGSEGV is caught, the stack is logged, and `--last-log` plus `symbolize.sh` (atos against the
    build's .dSYM) give on_signal (slog.c:205) → run_step (drive.c:544) → drive_step → main (app.c:968), on arm64 and
    under Rosetta;
  - a real scripted window on the runner's display: Cocoa swapchain, wheel, pinch, shot, exit 0, its session log in
    `$HOME/Library/Logs/bimble/sessions`.
  On arm64, links6 failed the strict 200 ms rule: event → app work 220.8 ms, event → fence 229.2 ms. The run was slow
  (links6 complete in 3,878 ms against 1,617 ms in round 3). The check stays as it is.
- **Round 5** (run 46152836736, `next` f4d002e merged): all green, the suites at 81/0 and 7/0 on arm64 and Rosetta. The
  test now names the slowest input: links6's was an `orbit` mid-drag at 124.9 ms app work (Rosetta: 103 ms).
  - frames.csv shows two UI-only frames of 776 triangles at that moment, with GPU times of 72 and 82 ms. The CPU stages
    stayed under 1.3 ms.
  - The app's "event → work done" runs from the event's SDL timestamp to the end of the UI build of the frame that takes
    it. With two frames in flight, the main thread first waits for the previous frame's fence (`app.c`
    `SDL_WaitForGPUFences(pend)`). So **a GPU stall shows up as app time**: here, the paravirtual GPU.
  - A lead for the owner's Linux session (a pick at 265 ms, view cube clicks at 106–165 ms): check whether frames.csv
    shows GPU-time spikes at those moments before looking for main-thread CPU work. Not measured here.
  - Also seen: frames.csv's `uibuild_ms` and `recui_ms` repeat one value over many UI-only frames, so these two columns
    look stale for frames that skip a stage (a reporting oddity in shared code, not fixed here).

## For the owner's MacBook

- The artifact is `macapp-arm64` of the latest green `macapp` run on PR #103: `bimble-<v>-macos-arm64.dmg`.
- First launch: open it once, then System Settings → Privacy & Security → Open Anyway (macOS 15+). Or run
  `xattr -dr com.apple.quarantine /Applications/bimble.app` once.
- One command gives the same summary as on Linux (Asahi versus macOS on the same GPU class):
  `/Applications/bimble.app/Contents/MacOS/bimble --offscreen --preset orbit-zoom --out ~/bimble-run model.ifc`.
- The session logs are in `~/Library/Logs/bimble/sessions`; `bimble --last-log` prints the newest.
